4.2.3　在线API的工具调用与简单RAG处理

在线API也额外提供了工具调用和简单的RAG（Retrieval-augmented Generation，检索增强生成）处理

RAG:通过动态检索外部知识库与生成式能力相结合，显著提升了模型在专业领域和实时数据场景下的表现。其核心机制主要包含两步：首先，用户输入问题和对应的参考文档，模型在生成过程对检索结果进行语义过滤与排序，剔除冗余信息；然后，将精选内容与原始Query拼接，输入大模型生成融合外部知识的最终回复。

5.1　RAG技术体系

传统RAG将用户问题转换为向量，并在知识库中进行语义匹配，检索出相关文档片段，再交由大模型生成答案。

RAG的核心流程可以分为3个主要环节:

​ 问题表示（经过编码器模型转换为语义向量）、

​ 知识检索（系统会将问题向量与预先构建的知识库中的文档向量进行相似度计算，采用最近邻搜索（如Faiss、Annoy等高效算法）找出最相关的若干个文档片段）

​ 答案生成 检索到的相关文档与原始问题拼接成上下文提示，作为输入提供给生成模型

在检索阶段若未能命中关键信息，生成模型可能会输出错误答案；而在生成阶段如果无法有效筛选和整合检索结果，也可能导致回答质量下降。因此，现代RAG系统往往引入强化学习、元学习等机制，持续优化各模块之间的协作效率，提升整体系统的鲁棒性和适应性。

医疗、法律、金融等专业领域，RAG能够有效弥补通用大模型在垂直场景下的知识短板

     Embedding-based：利用嵌入模型将文本映射到低维空间，根据语义相似度进行分块。

6.1.2　LLM、Workflow与Graph技术路线对比分析

1．LLM技术路线LLM技术路线以大语言模型为核心，通过深度学习方法对海量文本数据进行预训练，从而获得强大的语言理解与生成能力。LLM的核心优势在于其自动化训练能力、大规模数据处理能力和更强的上下文感知能力。基于LLM的智能系统能够灵活应对各种自然语言交互任务，如问答、翻译和内容生成等。此外，LLM还具备多模态生成的能力，使其在图像描述、语音识别等领域也表现出色。然而，LLM的局限性在于其“黑箱”特性，导致模型的行为难以预测和控制，同时对计算资源的需求较高，限制了其在资源受限环境下的部署。

2．Workflow技术路线Workflow技术路线更侧重于流程管理与业务规则的执行。它通过对工作流程及其各操作步骤之间的业务规则进行抽象和建模，提供了一种清晰的任务组织方式。Workflow系统通常采用集成化的框架，支持从模型建立、管理到运行和分析的完整生命周期管理。Workflow技术路线的优势在于其高度的可配置性和可控性，适用于需要严格遵循既定流程的应用场景，例如企业内部审批流程或生产线调度。然而，Workflow的灵活性相对较低，难以适应复杂或不断变化的任务需求，且在处理非结构化数据方面表现较弱

第9章　MCP与应用详解

核心目标在于标准化人工智能模型与外部数据源、工具之间的交互方式。

根据实际需求，在外部函数库中进行检索，找出合适的函数并调用它。

引导模型使用工具

这种方式就像给大模型提供一本详细的程序文档。在这份文档中，我们详细描述每个工具API的功能、参数以及返回值，告诉大语言模型在何时、何地可以调用这些API，并且当API被调用后，返回相应的API的JSON对象。

通过OpenAI库初始化了一个客户端，并设置了API密钥和基础URL。定义了一个get_weather()函数，用于模拟获取天气的功能。系统提示(system_prompt)中详细描述了对话系统的三个阶段：思考、工具调用和响应，并提供了一个示例说明如何调用get_weather工具，以回答天气相关的问题。

MCP通过定义一套统一的通信规范，成功打破了模型与外部系统之间的壁垒，使得大语言模型能够轻松、无缝地连接本地文件、数据库、API以及各类专业工具.

从架构层面来看，MCP主要由Host（主机）、Client（客户端）和Server（服务器）三大部分构成

MCP Host：作为发起请求的AI应用，它就像整个交互流程的指挥官。常见的如Claude、Cursor IDE等，这些应用在实际运行中会产生与外部资源交互的需求，从而触发整个MCP交互流程。·　

MCP Client：它运行在Host之中，扮演着格式转换大师的角色。当Host发起请求时，MCP Client会将请求格式化为结构化消息。这种结构化消息具有统一的格式和规范，便于后续的传输和处理，就像将杂乱的信息整理成有序的包裹，以便准确送达目的地。·　

MCP Server：作为轻量级中间件，它是连接本地或远程资源的桥梁。无论是庞大的数据库，还是功能丰富的API，MCP Server都能与之建立连接。它负责执行具体的操作，将操作结果返回，就如同一位高效的快递员，准确地将货物送达并带回反馈信息。

4．MCP的通信流程

(1)MCP Host向MCP Client发送请求，请求中包含了资源、工具和提示词等关键信息。

(2)MCP Client接收到请求后，将其格式化为结构化消息。

(3)格式化后的结构化消息被发送给MCP Server，MCPServer根据消息中的信息执行相应的操作，并将结果返回给MCP Client。

低层次检索（具体）。这一层次主要致力于检索特定的实体，以及与这些实体相关的属性或关系。该层次的查询以细节为导向，旨在提取图中各个节点或边的精确信息。

高层检索（抽象）。这一层级涉及更广泛的主题和总体概念。在该层级的查询会整合多个相关实体和关系中的信息，从而提供对更高层次概念的洞察与总结，而非具体的细节信息。

vLLM 是什么

vLLM 是一个专门用来部署大语言模型的推理引擎。

模型权重 + vLLM = 一个可以通过 HTTP 调用的大模型服务

它帮我们做这些事：

  • 把 /myData/aqwen3.5 里的 Qwen3.5-27B 权重加载到 PPU 显卡上

  • 自动处理 tokenizer（将文本转换token id 或者反过来）、chat template（自动处理对话模版，用特定格式区分system，user，assistant）、生成参数

    • temperature
控制随机性。越低越稳定，越高越发散。

top_p
控制采样范围。比如 0.9 表示只在累计概率前 90% 的 token 里采样。

max_tokens
最多生成多少 token。

stop
遇到指定字符串就停止生成。

repetition_penalty
降低重复输出的概率。
  - 提供 OpenAI 兼容接口，比如 /v1/chat/completions

    -  vLLM 提供的 HTTP API 格式尽量和 OpenAI 一样。可以通过OpenAI样式去请求当前大模型

  - 支持多卡并行，把 27B 模型切到 4 张 PPU 上跑

  - 管理显存（如果是FP16/BF16，则群众27B*2字节=54GB，此时还不包括 KV跟运行开销 --gpu-memory-utilization 0.85）、

  - KV Cache（把历史token在Transformer机制里面已经算过的key和value保存下来，下一步只需要计算新token，复用之前的缓存）、并发请求、流式输出等

第15章　多智能体框架LangGraph与聊天助手实战

LangGraph有3个关键元素：

  • State（状态）一个共享的数据结构通常是TypedDic
  • Nodes（节点）：编码代理逻辑的Python函数
  • Edges（边）：Python函数，基于当前的State决定接下来执行哪个Node

边：1．Normal Edges 2．Conditional Edges 3．Entry Point （Entry Point是图形启动时首先运行的节点。） 4．Conditional Entry Point（Conditional Entry Point允许根据自定义逻辑在不同节点之间开始。）
